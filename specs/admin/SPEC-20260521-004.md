# SPEC-20260521-004: Admin Role e Operações LGPD

**Status:** Aprovada
**Criada em:** 2026-05-21
**Atualizada em:** 2026-05-21
**Autor:** análise arquitetural
**Revisores:** —

---

## Contexto

O sistema usa RLS do Supabase com `auth.uid() = user_id` para isolamento de dados. Esta política impede qualquer operação cross-user — o que é correto para usuários finais, mas bloqueia operações administrativas legítimas e exigências da LGPD:

1. **Direito ao esquecimento (LGPD Art. 18):** Usuário solicita exclusão total da conta. O trigger `soft_delete_profile()` já existe no DB, mas não há endpoint de auto-exclusão acessível ao usuário.
2. **Acesso a audit logs:** Administradores precisam visualizar logs para investigação de incidentes — a RLS atual permite que usuários vejam apenas os próprios logs.
3. **Suporte:** Equipe de suporte precisa acessar dados de um usuário específico para diagnóstico (requer service role bypass de RLS).

O `SUPABASE_SERVICE_ROLE_KEY` já está configurado e validado (SPEC-20260521-001), mas não há `AdminSupabaseService` nem endpoints administrativos.

## Objetivo

Implementar: (1) endpoint de auto-exclusão de conta pelo próprio usuário, e (2) módulo `admin` com `AdminSupabaseService` (service role) para operações cross-user, protegido por claim de role no JWT.

## Requisitos Funcionais

| ID | Requisito | Prioridade |
|----|-----------|------------|
| RF-01 | `DELETE /users/me` — usuário exclui a própria conta (soft delete + anonymization) | Alta |
| RF-02 | Soft delete aciona trigger `soft_delete_profile()` que anonimiza nome e limpa preferences | Alta |
| RF-03 | Após exclusão, todos os tokens JWT do usuário são revogados (Supabase `auth.admin.deleteUser`) | Alta |
| RF-04 | Endpoint de auto-exclusão exige confirmação: body `{ confirm: true }` | Alta |
| RF-05 | `AdminSupabaseService` cria client com `SERVICE_ROLE_KEY` — separado do `SupabaseService` (anon) | Alta |
| RF-06 | `GET /admin/users` — listar usuários (paginado, apenas admin) | Média |
| RF-07 | `GET /admin/audit-logs` — listar audit logs com filtro por `user_id` e período (apenas admin) | Média |
| RF-08 | `DELETE /admin/users/:id` — admin exclui conta de qualquer usuário (LGPD compliance) | Média |
| RF-09 | Admin role identificado por `role: 'service_role'` no JWT do Supabase OU por campo em `profiles` | Alta |

## Requisitos Não-Funcionais

| ID | Requisito | Métrica de Aceite |
|----|-----------|------------------|
| RNF-01 | Segurança | Endpoints `/admin/*` bloqueados para não-admins com 403 |
| RNF-02 | Auditoria | Toda operação admin registra em `audit_logs` com `user_id` do admin |
| RNF-03 | Irreversibilidade | Exclusão de conta é permanente após 30 dias (hard delete agendado) |
| RNF-04 | LGPD prazo | Resposta ao pedido de exclusão em < 15 dias (Art. 18) — operação técnica deve ser imediata |

## Critérios de Aceite

- [ ] CA-01: `DELETE /users/me` com `{ confirm: true }` → 204 No Content; perfil anonimizado no DB
- [ ] CA-02: Após `DELETE /users/me`, tokens existentes retornam 401 nas próximas requisições
- [ ] CA-03: `DELETE /users/me` sem `{ confirm: true }` → 400 Bad Request
- [ ] CA-04: `GET /admin/users` com token de usuário comum → 403 Forbidden
- [ ] CA-05: `GET /admin/audit-logs?user_id=X` retorna logs do usuário X (apenas admin)
- [ ] CA-06: `AdminSupabaseService` nunca importado fora do módulo `admin` e do `AuthModule`
- [ ] CA-07: `SERVICE_ROLE_KEY` não aparece em nenhum response ou log de nível INFO/WARN

## Fora de Escopo

- Não inclui: UI de painel administrativo (Fase 2)
- Não inclui: Hard delete automático pós-30-dias (job de retenção — Fase 2)

- Não inclui: Gestão de roles via UI (admin atribuído manualmente via Supabase Dashboard no MVP)

## Notas Técnicas

**Estrutura do módulo admin:**
```
apps/api/src/modules/admin/
  admin.module.ts
  admin.controller.ts      ← endpoints /admin/*
  admin.service.ts
  guards/
    admin.guard.ts         ← verifica role='admin' no JWT payload
  services/
    admin-supabase.service.ts  ← client com SERVICE_ROLE_KEY
```

**AdminSupabaseService:**
```typescript
@Injectable()
export class AdminSupabaseService {
  readonly client: SupabaseClient;

  constructor(private configService: ConfigService) {
    this.client = createClient(
      this.configService.get('SUPABASE_URL')!,
      this.configService.get('SUPABASE_SERVICE_ROLE_KEY')!,
    );
  }
}
```

**Identificação de admin:** No MVP, admin é identificado por `role = 'service_role'` no payload JWT do Supabase. Para usuários admin criados via Supabase Dashboard, é possível definir `user_metadata.role = 'admin'` e verificar no payload JWT customizado. Avaliar qual abordagem o Supabase suporta melhor na implementação.

**Endpoint de auto-exclusão:**
```typescript
@Delete('me')
@UseGuards(SupabaseAuthGuard)
async deleteAccount(@UserId() userId: string, @Body() body: { confirm: boolean }) {
  if (!body.confirm) throw new BadRequestException('Confirmação necessária');
  await this.usersService.deleteAccount(userId);
  return { message: 'Conta excluída com sucesso' };
}
```

**Fluxo de `deleteAccount`:**
1. `supabase.auth.admin.deleteUser(userId)` — revoga sessões e marca user como deleted em `auth.users`
2. O trigger `on_auth_user_created` não actua aqui; o `soft_delete_profile()` é acionado via UPDATE ou DELETE na tabela `profiles`
3. Registrar `audit_logs`: `action = 'ACCOUNT_DELETED'`, `table_name = 'profiles'`, `record_id = userId`

**Atenção:** O trigger `soft_delete_profile()` atual está declarado mas não tem um `CREATE TRIGGER` associado na migration 001 — verificar e corrigir na implementação.
