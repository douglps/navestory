## 1. Contexto

O módulo de autenticação é a porta de entrada de todos os usuários do navestory. Existem registros dispersos em `stories.md`, dois ADRs, dois specs de hardening e uma spec de operações LGPD que tratam parcialmente do mesmo domínio, criando risco de divergência entre o que foi decidido, o que foi implementado e o que está pendente.

Esta spec unifica num único documento:

1. Cadastro de conta
2. Login (credenciais válidas e inválidas, bloqueio por tentativas)
3. Recuperação e redefinição de senha
4. Gestão de sessão — **com mudança de comportamento em relação ao ADR-003**
5. Resiliência (sistema indisponível, offline)
6. Alteração de credenciais via perfil (senhas)

A exclusão de conta (LGPD) permanece autorizada em `SPEC-20260521-004`; esta spec a referencia e não a reproduz.

## 2. Mudança de Comportamento — Lifecycle de Sessão

> **Esta seção supersede o ADR-003 na parte de lifecycle de sessão.**

### Antes (ADR-003)

- Access token: 15 min (fixo)
- Refresh token: 7 dias (implicitamente "lembrar de mim")
- Sem distinção de comportamento por preferência do usuário

### Agora (esta spec)

| Modo                     | Idle timeout             | Renovação                        | Expiração final                                                          |
| ------------------------ | ------------------------ | -------------------------------- | ------------------------------------------------------------------------ |
| **Sem "lembrar de mim"** | **30 min sem atividade** | Por interação ou mudança de rota | Ao atingir 30 min idle → logout                                          |
| **Com "lembrar de mim"** | Sem idle timeout         | Automática pelo SDK Supabase     | **7 dias** (604 800 s — TTL atual do access token no Supabase Dashboard) |

**Idle timeout (modo sem lembrar):**

- Um timer de 30 min é iniciado após o login
- É **resetado** a cada: click, keypress, scroll, touchstart, wheel, ou mudança de rota (Next.js router)
- Ao expirar: `supabase.auth.signOut()` → redirect `/login?session=expired`

**Renovação silenciosa:**

- Em ambos os modos: quando o access token estiver a menos de 5 min de expirar E houver atividade recente, o SDK Supabase renova automaticamente
- Sem atividade: o token expira e o idle timer ou a expiração do refresh token força o logout

**Implementação Supabase:**

- Sem lembrar: `signInWithPassword({ ... })` padrão — idle timer de 30 min via `useActivityTracker` encerra a sessão por inatividade
- Com lembrar: mesmo `signInWithPassword` — sem idle timer; sessão expira naturalmente em 7 dias (604 800 s, TTL configurado no Supabase Dashboard — não alterar)

## 4. Regras de Negócio

### 4.1 Senha

- Mínimo: 8 caracteres, 1 letra maiúscula, 1 número
- Validação idêntica no Zod do frontend e em `@navestory/validators` (nunca apenas no cliente)
- Toggle show/hide obrigatório com `aria-label` alternando "Mostrar senha" / "Ocultar senha"

### 4.2 Rate Limiting (substitui SPEC-20260521-001 §RF-SEC-004)

| Endpoint                      | Limite  | Janela | Dimensão |
| ----------------------------- | ------- | ------ | -------- |
| `POST /auth/register`         | 5 req   | 15 min | por IP   |
| `POST /auth/login`            | 10 req  | 15 min | por IP   |
| `POST /auth/recover-password` | 3 req   | 15 min | por IP   |
| Demais endpoints              | 100 req | 60 s   | por IP   |

Resposta `429`: header `Retry-After` com segundos restantes. Frontend exibe countdown derivado do header.

### 4.3 Bloqueio de tentativas de login

- Após **5 tentativas inválidas consecutivas**: acesso bloqueado por **15 min**
- Contador implementado em cache (Redis ou Supabase) e zerado após login bem-sucedido
- Bloqueio por usuário (email) — independente do rate limit por IP

### 4.4 Anti-enumeração

- `POST /auth/login` → sempre `INVALID_CREDENTIALS` (nunca indica se o email existe)
- `POST /auth/recover-password` → sempre HTTP 200 com mensagem genérica
- A distinção entre "email não existe" e "senha errada" nunca é exposta ao cliente

### 4.5 `profile_type`

- Campo obrigatório no `RegisterDto`
- Default: `'autonomous'`
- Gestor de Frota requer seleção explícita no formulário

### 4.6 Sessão simultânea (multi-device)

- JWT stateless: comportamento aceito no MVP. Logout em um dispositivo não invalida o outro.
- Documentado como limitação de segurança — revisão prevista para fase 2

## 5. User Stories

### 5.1 Cadastro

---

#### STORY-REG-01 — Registrar nova conta

Como Carlos, motorista autônomo,  
Quero criar uma conta com meu e-mail, senha e tipo de perfil,  
Para que eu comece a registrar veículos e despesas.

**Critérios de Aceitação**

**Cenário 1: Registro bem-sucedido**

```gherkin
Dado que o usuário preenche nome, e-mail único, senha válida e tipo de perfil
Quando clica em "Criar conta"
Então a conta é criada no Supabase Auth + perfil criado atomicamente em `profiles`
E o usuário é redirecionado para /dashboard com sessão ativa
E um evento REGISTER é registrado em audit_logs
```

**Cenário 2: E-mail já cadastrado**

```gherkin
Dado que o e-mail informado já existe na plataforma
Quando o usuário submete o formulário
Então a API retorna HTTP 409 com código EMAIL_ALREADY_REGISTERED
E o frontend exibe: "Este e-mail já está cadastrado. [Fazer login / Esqueci a senha]"
E não exibe mensagem genérica de erro
```

**Cenário 3: Senha fraca**

```gherkin
Dado que o usuário informa senha que não atende os critérios mínimos
Quando tenta submeter o formulário
Então a validação Zod no frontend bloqueia o envio
E exibe inline: "A senha deve ter no mínimo 8 caracteres, 1 maiúscula e 1 número"
E a requisição não é disparada ao backend
```

**Cenário 4: Rate limit de registro atingido**

```gherkin
Dado que o IP atingiu 5 requisições em 15 minutos
Quando o usuário tenta se registrar
Então a API retorna HTTP 429 com header Retry-After
E o frontend exibe: "Muitas tentativas. Aguarde X minutos." com countdown
```

**Cenário 5: Falha na criação do perfil (rollback)**

```gherkin
Dado que a conta Supabase Auth foi criada com sucesso
Quando a criação do perfil em `profiles` falha (ex: timeout de DB)
Então auth.service faz rollback via auth.admin.deleteUser(userId)
E retorna HTTP 500 sem stack trace ou detalhes de schema
E o usuário pode tentar novamente sem duplicata no Auth
```

**Estimativa:** 5 pts — Transação com rollback, validação dual (frontend + backend), 5 cenários testáveis  
**Dependências:** Nenhuma

### 5.2 Login

---

#### STORY-01 — Login com credenciais válidas

Como qualquer usuário cadastrado (motorista, gestor ou administrador),  
Quero autenticar-me com e-mail e senha,  
Para que eu acesse as funcionalidades da plataforma de acordo com meu perfil.

**Critérios de Aceitação**

**Cenário 1: Login bem-sucedido sem "lembrar de mim"**

```gherkin
Dado que o usuário possui conta ativa e não marca "Lembrar de mim"
Quando preenche e-mail e senha corretos e clica em "Entrar"
Então é autenticado com persistSession: false (sessão apenas em memória)
E é redirecionado para o dashboard correspondente ao seu perfil (role)
E o idle timer de 30 minutos é iniciado
E um evento LOGIN é registrado em audit_logs
```

**Cenário 2: Login bem-sucedido com "lembrar de mim"**

```gherkin
Dado que o usuário marca "Lembrar de mim" antes de fazer login
Quando preenche e-mail e senha corretos e clica em "Entrar"
Então é autenticado com persistSession: true (sessão em localStorage)
E é redirecionado para o dashboard correspondente ao seu perfil
E nenhum idle timer de 30 minutos é iniciado
```

**Cenário 3: Redirect após acesso a rota protegida**

```gherkin
Dado que o usuário tentou acessar uma rota protegida sem estar autenticado
Quando conclui o login com sucesso
Então é redirecionado de volta à rota que tentou acessar originalmente
```

**Cenário 4: Usuário já autenticado acessa /login**

```gherkin
Dado que o usuário já possui sessão ativa
Quando acessa diretamente a URL /login
Então o middleware de rota redireciona automaticamente para /dashboard
E o formulário de login não é renderizado
```

**Estimativa:** 3 pts — Autenticação via Supabase, dois modos de persistência, redirect  
**Dependências:** Nenhuma

#### STORY-02 — Login com credenciais inválidas

Como usuário que errou e-mail ou senha,  
Quero receber feedback claro e seguro sobre o erro,  
Para que eu saiba que minha entrada está incorreta sem expor informações de segurança.

**Critérios de Aceitação**

**Cenário 1: Senha incorreta ou e-mail inexistente**

```gherkin
Dado que o usuário informa credenciais inválidas (qualquer combinação)
Quando clica em "Entrar"
Então a mensagem "E-mail ou senha inválidos" é exibida
E nenhuma informação sobre qual campo está errado é revelada
E o campo de senha é limpo automaticamente
E o contador de tentativas para o e-mail informado é incrementado
E quando restam 2 ou menos tentativas antes do bloqueio, a contagem é exibida junto à mensagem
```

**Cenário 2: Campos em branco**

```gherkin
Dado que o usuário não preencheu e-mail ou senha
Quando clica em "Entrar"
Então os campos obrigatórios são destacados com erro inline
E a requisição ao backend não é disparada
```

**Estimativa:** 2 pts — Tratamento de erro + anti-enumeração  
**Dependências:** STORY-01

#### STORY-03 — Bloqueio por tentativas excessivas de login

Como usuário que excedeu o limite de tentativas,  
Quero ser informado do bloqueio temporário e do tempo restante,  
Para que eu entenda o motivo e saiba quando posso tentar novamente.

**Critérios de Aceitação**

**Cenário 1: Bloqueio ativado na 5ª tentativa**

```gherkin
Dado que o usuário falhou 4 vezes consecutivas para o mesmo e-mail
Quando realiza a 5ª tentativa inválida
Então o acesso é bloqueado por 15 minutos para aquele e-mail
E a mensagem "Muitas tentativas. Tente novamente em 15 minutos" é exibida
E o botão "Entrar" fica desabilitado com countdown regressivo visível
```

**Cenário 2: Tentativa durante bloqueio ativo**

```gherkin
Dado que o usuário está com acesso bloqueado
Quando tenta submeter o formulário (mesmo com credenciais corretas)
Então o sistema rejeita a tentativa antes de consultar o Supabase Auth
E exibe o tempo restante do bloqueio atualizado
```

**Cenário 3: Desbloqueio automático após 15 minutos**

```gherkin
Dado que o bloqueio de 15 minutos expirou
Quando o usuário acessa a página de login
Então o botão e o contador são removidos
E o usuário pode tentar novamente normalmente
E um login bem-sucedido zera o contador de tentativas
```

**Cenário 4: Aviso progressivo antes do bloqueio**

```gherkin
Dado que o usuário errou as credenciais consecutivamente para o mesmo e-mail
Quando restam 3 ou mais tentativas antes do bloqueio
Então apenas "E-mail ou senha inválidos." é exibido, sem mencionar o contador
Quando restam exatamente 2 tentativas
Então "E-mail ou senha inválidos. 2 tentativas restantes." é exibido
Quando resta exatamente 1 tentativa
Então "E-mail ou senha inválidos. Última tentativa antes do bloqueio temporário." é exibido
```

**Estimativa:** 5 pts — Rate limiting por e-mail em cache, feedback no frontend, integração com STORY-02  
**Dependências:** STORY-02

#### STORY-04 — Solicitar redefinição de senha

Como usuário que esqueceu sua senha,  
Quero solicitar um link de redefinição via e-mail,  
Para que eu recupere o acesso à minha conta sem precisar de suporte.

**Critérios de Aceitação**

**Cenário 1: Solicitação com e-mail cadastrado**

```gherkin
Dado que o usuário informa um e-mail existente na plataforma
Quando clica em "Enviar link de redefinição"
Então o sistema envia um e-mail com link de redefinição válido por 1 hora (via Supabase)
```

**Cenário 2: Solicitação com e-mail não cadastrado**

```gherkin
Dado que o usuário informa um e-mail que não existe
Quando clica em "Enviar link de redefinição"
Então o sistema exibe a mesma mensagem genérica (anti-enumeração)
E nenhum e-mail é enviado
E a resposta HTTP é sempre 200
```

**Cenário 3: Falha no envio de e-mail (serviço indisponível)**

```gherkin
Dado que o serviço de e-mail do Supabase Auth está indisponível
Quando o usuário solicita a redefinição
Então o sistema registra o erro em log interno
E exibe: "Não foi possível enviar o e-mail. Tente novamente em instantes."
E permite nova tentativa imediatamente (sem bloquear)
```

**Cenário 4: Reenvio de e-mail**

```gherkin
Dado que o usuário está na tela /recover-password após já ter solicitado
Quando clica em "Reenviar e-mail"
Então o sistema dispara nova solicitação (limitado por rate limit: 3 req/15min)
E o botão fica desabilitado por 60 segundos com countdown visual
```

**Estimativa:** 5 pts — Anti-enumeração, tratamento de falha de e-mail, cooldown de reenvio  
**Dependências:** Nenhuma

### 5.4 Gestão de Sessão

---

#### STORY-06 — Sessão persistente com "lembrar de mim"

Como usuário recorrente da plataforma,  
Quero manter minha sessão ativa entre visitas com a opção "lembrar de mim",  
Para que eu não precise fazer login toda vez que acesso o sistema.

**Critérios de Aceitação**

**Cenário 1: Login com "lembrar de mim" marcado**

```gherkin
Dado que o usuário marca "Lembrar de mim" antes de fazer login
Quando autentica com sucesso
Então a preferência é salva em sessionStorage (navestory_session_remember = true)
E nenhum idle timer de 30 minutos é iniciado
E a sessão expira naturalmente após 7 dias (604 800 s — TTL do Supabase Dashboard)
E ao fechar e reabrir o browser na mesma sessão, o usuário permanece autenticado
```

**Cenário 2: Login sem "lembrar de mim"**

```gherkin
Dado que o usuário não marca "Lembrar de mim"
Quando autentica com sucesso
Então a preferência é salva em sessionStorage (navestory_session_remember = false)
E o idle timer de 30 minutos é iniciado pelo useActivityTracker no DashboardLayout
E após 30 min de inatividade, a sessão é encerrada com redirect /login?session=expired&reason=idle
```

**Estimativa:** 5 pts — Checkbox, preferência em sessionStorage, idle timer via useActivityTracker  
**Dependências:** STORY-01

#### STORY-07a — Renovação automática de sessão por interação ou mudança de rota

Como usuário autenticado em sessão sem "lembrar de mim",  
Quero que minha sessão seja renovada automaticamente enquanto estou usando o app,  
Para que eu não seja deslogado durante uma tarefa ativa.

**Critérios de Aceitação**

**Cenário 1: Renovação silenciosa por interação do usuário**

```gherkin
Dado que o usuário está autenticado sem "lembrar de mim"
E o idle timer ainda não expirou (menos de 30 min sem atividade)
Quando o usuário realiza qualquer ação (click, tecla, scroll, toque)
Então o idle timer é resetado para 30 minutos
E se o access token estiver a menos de 5 min de expirar, o SDK Supabase o renova silenciosamente
E o usuário não percebe nenhuma interrupção
```

**Cenário 2: Renovação por mudança de rota**

```gherkin
Dado que o usuário está autenticado e navega entre páginas do app
Quando ocorre uma mudança de rota (Next.js router.events)
Então o idle timer é resetado para 30 minutos
E o token é renovado silenciosamente se necessário
```

**Cenário 3: Idle de 30 minutos atingido (sem "lembrar de mim")**

```gherkin
Dado que o usuário está autenticado sem "lembrar de mim"
E não houve nenhuma interação nos últimos 30 minutos
Quando o idle timer expira
Então supabase.auth.signOut() é chamado
E o usuário é redirecionado para /login?session=expired
E um toast explica: "Sua sessão expirou por inatividade. Faça login novamente."
```

**Cenário 4: Sessão de "lembrar de mim" expirada (30 dias)**

```gherkin
Dado que o usuário está autenticado com "lembrar de mim"
E o refresh token de 30 dias expirou
Quando o usuário tenta realizar qualquer ação
Então o SDK Supabase detecta o token inválido e emite SIGNED_OUT
E useAuthWatcher redireciona para /login?session=expired
E um toast explica: "Sua sessão expirou. Faça login novamente."
```

**Notas de implementação:**

- Eventos monitorados: `click`, `keypress`, `scroll`, `touchstart`, `wheel`
- Mudança de rota: `router.events.on('routeChangeComplete', resetIdleTimer)`
- O hook `useActivityTracker()` encapsula este comportamento e é montado no layout raiz
- Diferente do `useAuthWatcher()` existente (que apenas detecta SIGNED_OUT) — ambos coexistem

**Estimativa:** 8 pts — Hook de atividade, integração com router Next.js, dois modos de sessão, múltiplos cenários  
**Dependências:** STORY-01, STORY-06

#### STORY-07b — Preservação de estado em formulários durante expiração de sessão

Como usuário autenticado preenchendo um formulário longo,  
Quero que os dados preenchidos não sejam perdidos quando minha sessão expirar,  
Para que eu não precise preencher tudo de novo após fazer login.

**Critérios de Aceitação**

**Cenário 1: Sessão expira durante preenchimento de formulário**

```gherkin
Dado que o usuário está preenchendo um formulário com dados não salvos
Quando o idle timer de 30 minutos expira
Então o sistema tenta renovar o token antes de deslogar (1 tentativa via refreshSession())
E se a renovação falhar, o estado atual do formulário é salvo em sessionStorage
E o usuário é redirecionado para /login?session=expired&redirect=[rota_atual]
E ao fazer login com sucesso, é redirecionado de volta à rota com os dados restaurados
```

**Cenário 2: Restauração de formulário após login**

```gherkin
Dado que o formulário foi salvo em sessionStorage antes do logout por inatividade
Quando o usuário faz login com sucesso e é redirecionado para a rota do formulário
Então os campos são restaurados com os valores que estavam preenchidos
E um banner discreto informa: "Seus dados foram restaurados do rascunho anterior"
```

**Cenário 3: Formulário sem dados preenchidos**

```gherkin
Dado que o formulário está vazio quando a sessão expira
Quando o usuário faz login e retorna à rota
Então nenhum dado é restaurado e o formulário é exibido em branco normalmente
```

**Notas de implementação:**

- Formulários candidatos: `/expenses/new`, `/maintenance/new`, `/vehicles/new`
- Persistência: `sessionStorage` (não `localStorage`) — dados limpos ao fechar o browser
- A chave de sessionStorage segue o padrão: `navestory_form_draft_[route_path]`
- Componente `<FormDraftGuard>` encapsula a lógica de save/restore por formulário

**Estimativa:** 5 pts — Componente reutilizável, integração com idle timer, 3 formulários candidatos  
**Dependências:** STORY-07a

#### STORY-08 — Indisponibilidade do serviço de autenticação

Como usuário que tenta fazer login durante instabilidade do Supabase,  
Quero receber uma mensagem clara sobre a indisponibilidade do sistema,  
Para que eu entenda que o problema não é meu e saiba que devo tentar mais tarde.

**Critérios de Aceitação**

**Cenário 1: Supabase Auth retorna erro 5xx**

```gherkin
Dado que o Supabase Auth está retornando erros de servidor (5xx)
Quando o usuário tenta fazer login
Então o sistema captura o erro e exibe: "Serviço temporariamente indisponível. Tente novamente."
E nenhum stack trace ou mensagem técnica é exibido (HttpExceptionFilter ativo)
E o erro é registrado internamente com timestamp e código de resposta
```

**Cenário 2: Timeout na requisição de autenticação (> 10 segundos)**

```gherkin
Dado que a requisição ao Supabase ultrapassa 10 segundos sem resposta
Quando o timeout é atingido pelo cliente
Então a requisição é cancelada pelo frontend
E o botão "Entrar" volta ao estado normal (sem loading infinito)
E a mensagem exibe: "A conexão demorou demais. Verifique sua internet ou tente novamente."
```

**Cenário 3: Dispositivo offline (sem conexão)**

```gherkin
Dado que o dispositivo não tem conexão com a internet
Quando o usuário tenta fazer login
Então o frontend detecta a ausência de conexão via navigator.onLine antes de disparar
E exibe: "Sem conexão com a internet. Verifique sua rede."
E não dispara requisição desnecessária ao backend
```

**Estimativa:** 5 pts — Tratamento de erros HTTP, detecção offline no Next.js, timeout configurável  
**Dependências:** STORY-01

### 5.5 Segurança de Conta — Alterar Credenciais

---

#### STORY-SEC-01 — Alterar senha via perfil

Como usuário autenticado,  
Quero alterar minha senha diretamente na seção de segurança do perfil,  
Para que eu possa renovar credenciais sem passar pelo fluxo de "Esqueci minha senha".

**Critérios de Aceitação**

**Cenário 1: Alteração bem-sucedida**

```gherkin
Dado que o usuário está autenticado e acessa /profile (seção "Segurança")
Quando clica em "Alterar senha"
Então o sistema aciona o fluxo de reset de senha Supabase por e-mail
E exibe: "Enviamos um link de alteração para seu e-mail cadastrado"
E o usuário segue o fluxo de STORY-05 para redefinir
```

**Cenário 2: Alterar e-mail**

```gherkin
Dado que o usuário quer alterar seu e-mail
Quando acessa /profile e edita o campo de e-mail
Então o sistema aciona a API Supabase de troca de e-mail
E envia e-mail de confirmação para o novo endereço
E o e-mail só é alterado após confirmação no novo endereço
```

**Estimativa:** 3 pts — Delegação ao fluxo Supabase, sem lógica própria de troca de senha  
**Dependências:** STORY-04, STORY-05

## 8. Componentes e Hooks Novos

| Artefato               | Tipo           | Responsabilidade                                                                         |
| ---------------------- | -------------- | ---------------------------------------------------------------------------------------- |
| `useActivityTracker()` | Hook (Next.js) | Monitora eventos do usuário e mudanças de rota; gerencia idle timer de 30 min            |
| `<FormDraftGuard>`     | Componente     | Salva/restaura estado de formulário via sessionStorage em caso de logout por inatividade |
| `useAuthWatcher()`     | Hook existente | Detecta SIGNED_OUT e redireciona — complementar ao useActivityTracker                    |

**Ordem de responsabilidades:**

- `useActivityTracker` → gerencia idle timer e renova token proativamente
- `useAuthWatcher` → captura eventos SIGNED_OUT emitidos pelo Supabase SDK (qualquer causa)
- Ambos montados no layout raiz; `<FormDraftGuard>` montado apenas nos formulários candidatos
