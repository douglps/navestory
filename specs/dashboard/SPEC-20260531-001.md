## 1. Contexto

O dashboard atual (`apps/web/app/(dashboard)/dashboard/page.tsx`) é um Server Component estático que exibe KPIs, ações rápidas, gráficos e alertas de manutenção numa única coluna sem diferenciação de contexto por veículo. Os problemas identificados são:

1. **Gráficos mockados** — `CostPerKmChart`, `FuelConsumptionChart` e `ExpenseCategoryPie` renderizam dados estáticos, não os dados reais do usuário autenticado.
2. **Estado de veículo ativo duplicado** — `FleetAside` mantém um estado local próprio, desconectado do `?vehicleId=` da URL e do store Zustand global (`use-dashboard-store`), gerando inconsistência de contexto entre componentes.
3. **Ausência de visão de saúde da frota** — não existe agrupamento visual por veículo com indicador de risco (documentos vencidos, manutenções atrasadas). O usuário precisa navegar a múltiplas telas para entender o estado da frota.
4. **Dock de ações fragmentado** — o `FloatingIAButton` existe como componente separado do dock de ações rápidas, criando dois pontos de entrada para IA e ocupando espaço de tela de forma redundante.
5. **Campo `odometer` não obrigatório no abastecimento** — ausência do quilômetro atual no momento do abastecimento impede o cálculo de consumo e custo/km, tornando as análises inúteis para frotas que não preenchem o campo.
6. **Campos de documentos ausentes no banco** — a tabela `vehicles` não possui `ipva_due_date`, `insurance_expires_at` nem `crlv_expires_at`, impossibilitando alertas de documentos e composição do score de saúde.
7. **Tabela `fines` inexistente** — multas são registradas como despesas genéricas sem categoria dedicada, perdendo rastreabilidade.

Esta spec define a arquitetura, os requisitos e os critérios de aceite do redesign, dividido em três sprints.

---

## 2. Objetivo

Entregar um dashboard mobile-first em duas zonas funcionais claramente separadas — **Fleet Command** (visão consolidada da frota) e **Vehicle Spotlight** (análise contextual por veículo) — com estado global sincronizado, gráficos conectados a dados reais e um dock unificado de ações rápidas, resolvendo os sete problemas descritos no contexto.

## 8. Riscos e Mitigações

| # | Risco | Probabilidade | Impacto | Mitigação |
|---|-------|--------------|---------|-----------|
| R-01 | Registro no veículo errado — usuário com múltiplos veículos aciona uma ação rápida sem perceber qual está ativo | Alta | Alto — dado registrado no veículo errado, difícil de desfazer | O veículo ativo é exibido em destaque no chip sticky e pré-selecionado (mas editável via `Combobox`) em todos os formulários do dock. Toast de confirmação pós-registro exibe o nome do veículo e oferece "Desfazer". |
| R-02 | Overload de alertas para frotas com 4+ veículos — barra de alertas se torna ruído e o usuário a ignora | Média | Médio — perda de eficácia dos alertas | Máximo absoluto de 3 alertas na `FleetAlertBar`. Lógica de priorização: vencido > vence hoje > vence amanhã > vence em 7 dias. Demais alertas acessíveis via link de overflow. |
| R-03 | Transição ambígua entre zonas — usuário não percebe que a Zona B está filtrando por um veículo específico | Média | Médio — análise interpretada como dados da frota toda | Chip sticky com fundo diferenciado (`bg-primary/10`) e separador visual com `border-t-2` entre Zona A e Zona B. O chip é o único elemento a indicar qual veículo está ativo. |
| R-04 | Odômetro não preenchido quebra análises — `custo/km` retorna infinito ou NaN | Alta | Alto — KPI inútil e gráfico quebrado | Campo `odometer` obrigatório no formulário de abastecimento (RF-BD-04). Em KPIs onde o cálculo é impossível (odômetro ausente), exibir "—" com tooltip "Registre o odômetro no próximo abastecimento". |
| R-05 | Inconsistência de estado entre URL, store e FleetAside ao usar botão "Voltar" do browser | Média | Médio — estado stale no store após navegação | Subscrever `router.events` para sincronizar `activeVehicleId` com `searchParams` ao montar o componente (RF-ST-03). Usar `router.replace` (não `push`) ao atualizar o `?vehicleId=` para evitar entradas extras no histórico. |
| R-06 | Migration em produção com dados existentes — colunas novas (`ipva_due_date` etc.) são `NULL` para todos os veículos existentes | Alta | Baixo — dados ausentes, não corrompidos | Colunas são anuláveis por definição. O score de saúde trata `NULL` como "não preenchido" (sem penalidade). O formulário de edição de veículo exibe os novos campos como opcionais no primeiro acesso. |
| R-07 | Custo de queries — Zona A faz múltiplas queries paralelas (KPIs + cards por veículo + alertas) | Média | Médio — aumento de latência perceptível | Usar `Promise.all` para paralelizar (já aplicado no dashboard atual). Explorar `supabase.rpc` para consolidar dados em função PostgreSQL na Sprint 2. Implementar stale-while-revalidate via React cache para dados de frota (atualização a cada 5 min). |

## 12. Notas Técnicas

### 12.1 Arquitetura de estado

O estado `activeVehicleId` percorre três camadas:
1. **URL** (`?vehicleId=`) — fonte de verdade para Server Components e deep links.
2. **Store Zustand** (`useDashboardStore`) — fonte de verdade para Client Components sincronizados em tempo real.
3. **localStorage** (`nave_active_vehicle`) — persistência entre sessões, lida na inicialização do store.

A sincronização URL ↔ store deve ser feita no componente `DashboardPage` ao montar: se `searchParams.vehicleId` estiver presente, inicializa o store com esse valor. Ao mudar via store, atualizar a URL com `router.replace` para não criar entradas no histórico.

### 12.2 Server Component vs. Client Component

A `DashboardPage` é um Server Component (busca dados no servidor). A Zona B e o Dock precisam de interatividade (Client Components). A recomendação é:

- `DashboardPage` (Server): busca dados da Zona A, renderiza `VehicleHealthCard`s e `FleetAlertBar` com dados serializados.
- `VehicleSpotlight` (Client): lê `activeVehicleId` do store e dispara suas próprias queries via Server Actions ou route handlers.
- `ActionDock` (Client): lê `activeVehicleId` do store para pré-preencher formulários.

### 12.3 Migração incremental

As Zonas A e B podem ser entregues de forma incremental sem quebrar o dashboard atual:

- Sprint 1: `FleetAlertBar` + `VehicleHealthCard` substituem a seção de "Manutenções críticas" atual. O restante do dashboard continua intacto.
- Sprint 2: `VehicleSpotlight` é adicionado abaixo da área atual. Os gráficos mockados são substituídos pelos reais.
- Sprint 3: Score de saúde é ativado nos `VehicleHealthCard`s.

### 12.4 Chaves de localStorage

Para evitar colisão com outras specs (`SPEC-20260524-001`):

| Chave | Dono | Conteúdo |
