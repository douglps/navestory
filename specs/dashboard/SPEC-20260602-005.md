# SPEC-20260602-005: Monitor do Sistema — Audit Log Dashboard

**Status:** Aprovado
**Criada em:** 2026-06-02
**Atualizada em:** 2026-06-02
**Autor:** douglps

## Contexto

O Nave SaaS registra cada mutação relevante (criar, atualizar, excluir veículos, despesas e manutenções) em uma tabela `audit_logs` por compliance com LGPD (C2). O registro acontece em dois pontos independentes:

- **Backend (API NestJS):** `AuditService.log()` — usado nas operações REST que passam pelo NestJS.
- **Frontend (Server Actions):** `writeAuditLog()` helper — usado nas Server Actions do Next.js que operam diretamente no Supabase sem passar pela API.

A página `/dashboard/monitor` exibe esse histórico ao próprio usuário em uma interface operacional com KPIs e tabela de eventos, permitindo auditoria pessoal das operações realizadas. Este documento formaliza retroativamente os requisitos de ambas as camadas (infraestrutura de log + UI de visualização).

---

## Objetivo

Garantir que toda mutação de dados do usuário seja registrada de forma fire-and-forget em `audit_logs`, e que o usuário possa visualizar as últimas 100 operações em uma página de monitor com KPIs por domínio e tabela de eventos com timestamp relativo, badge de ação e detalhes filtrados.

---

## Requisitos Funcionais

### Infraestrutura de Audit Log

| ID | Requisito | Prioridade |
|----|-----------|------------|
| RF-01 | Toda Server Action mutante (criar/atualizar/excluir veículo, despesa, manutenção) chama `writeAuditLog()` após o sucesso da operação | Alta |
| RF-02 | `writeAuditLog()` é fire-and-forget: erros de escrita são silenciados via try/catch e nunca propagam para o usuário | Alta |
| RF-03 | `AuditService.log()` no backend injeta automaticamente `timestamp: ISO` no campo `changes` antes de inserir | Alta |
| RF-04 | `AuditService.log()` é fire-and-forget: erros são logados via `Logger` mas nunca relançados | Alta |
| RF-05 | `audit_logs.user_id` é `ON DELETE SET NULL` — logs são preservados mesmo após exclusão da conta do usuário | Média |
| RF-06 | O campo `changes` (JSONB) não armazena PII — campos como `user_id`, `deleted_at`, `photo_url`, `photo_thumbnail_url` são filtrados na exibição (e devem ser evitados no registro) | Alta |

### Ações auditadas

| ID | Requisito | Prioridade |
|----|-----------|------------|
| RF-07 | Ações registradas pelos Server Actions (frontend): `Criação de Veículo`, `Atualização de Dados`, `Exclusão de Veículo`, `Criação de Despesa`, `Atualização de Despesa`, `Exclusão de Despesa`, `Criação de Manutenção`, `Atualização de Manutenção`, `Exclusão de Manutenção`, `Conclusão de Manutenção` | Alta |

## Critérios de Aceite

- [ ] CA-01: Criar uma despesa via Server Action → entrada `{ action: "Criação de Despesa", table_name: "expenses" }` aparece em `audit_logs` na página Monitor
- [ ] CA-02: Falha simulada no insert de `audit_logs` (ex: timeout) → operação principal (criar despesa) retorna sucesso normalmente
- [ ] CA-03: Página `/dashboard/monitor` sem sessão → redirect para `/login`
- [ ] CA-04: Página exibe KPI "Total" igual ao número de linhas na tabela de eventos
- [ ] CA-05: Coluna "Detalhes" não exibe campos `user_id`, `deleted_at`, `photo_url` ou `photo_thumbnail_url`
- [ ] CA-06: Entrada com `created_at` de 30 segundos atrás exibe "agora"
- [ ] CA-07: Entrada com `created_at` de 90 minutos atrás exibe "1h atrás"
- [ ] CA-08: `AuditService.log()` no backend sempre inclui `timestamp` no campo `changes`
- [ ] CA-09: Após `DELETE /users/me`, registros em `audit_logs` do usuário têm `user_id = NULL` (não são excluídos)

## Notas Técnicas

### Dois escritores independentes de audit log

O sistema tem duas implementações de escrita em `audit_logs` sem compartilhamento de código:

| | Backend `AuditService` | Frontend `writeAuditLog` |
|---|---|---|
| Cliente Supabase | `AdminSupabaseService` (service role) | `createClient()` (user JWT) |
| Injeção de `timestamp` | Automática em `changes` | Não faz |
| Logging de erro | `Logger.error()` | Silencia completamente |
| Tipo de `action` | String livre | `AuditAction` union type |

Essa dualidade pode gerar inconsistência no formato dos registros. Unificar em uma única abstração é recomendado como melhoria futura.

### RLS ausente em `audit_logs`

A tabela `audit_logs` **não tem RLS habilitado** no schema inicial (`001_initial_schema.sql`). A segurança de leitura depende exclusivamente do filtro `.eq('user_id', user.id)` na query da página Monitor. Qualquer acesso direto ao Supabase sem esse filtro expõe logs de todos os usuários. Recomendado: adicionar policy `FOR SELECT USING (auth.uid() = user_id)`.

### `record_id` como TEXT disfarçado de UUID

O campo `record_id` é `UUID NOT NULL` no banco, mas o frontend passa strings como `'new'` (em `vehicle-actions.ts`) que não são UUIDs válidos. O Supabase provavelmente silencia o erro de tipo (ou lança e é capturado pelo try/catch do `writeAuditLog`). Isso significa que parte dos registros pode estar com `record_id` inválido.

### `audit_logs` sem type no `database.types.ts`

A tabela `audit_logs` não aparece no `database.types.ts` gerado, daí o cast `as any` na query do Monitor. O tipo `AuditRow` está definido localmente na página, criando divergência com o schema real.

### Cobertura de ações

Operações via Server Actions têm cobertura completa de audit log. Operações REST (NestJS) têm cobertura parcial — apenas as rotas onde `AuditService.log()` foi explicitamente chamado (veículos, despesas, manutenções no backend). Operações como exclusão via `vehicles.ts` Server Action **e** exclusão via `DELETE /vehicles/:id` REST podem gerar dois registros para a mesma operação se ambas forem usadas.
