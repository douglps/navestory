# SPEC-20260602-005: Histórico de Atividades — Audit Log do Usuário

**Status:** Aprovado
**Criada em:** 2026-06-02
**Atualizada em:** 2026-07-18
**Autor:** Douglas Lopes (lps.doug@protonmail.com)
**Revisores:** —

---

## Contexto

O navestory SaaS registra cada mutação relevante do usuário (criar, atualizar, excluir veículos, despesas, manutenções, multas, custos recorrentes e ciclos de odômetro) em uma tabela `audit_logs` por compliance com LGPD (C2). O registro tem **um único escritor**: `AuditService.log()`, no backend NestJS, chamado por toda operação que passa pela API REST. Não existe (nem nunca existiu) escrita direta em `audit_logs` a partir do frontend — o projeto não usa Server Actions do Next.js para mutação (decisão registrada em T3.9 de `docs/IMPLEMENTATION_STRATEGY.md`); `apps/web` consome exclusivamente a API via `apiClient`.

A página `/atividades` exibe esse histórico ao próprio usuário em uma interface com KPIs e tabela de eventos, permitindo auditoria pessoal das operações realizadas. O nome da página evita o termo genérico "Monitor" para não ser confundido com o dashboard técnico de observabilidade (Sentry/Pino, `SPEC-20260716-002`) — esta spec cobre uma trilha de auditoria de ações do usuário para fins de compliance, não monitoramento técnico de erros/performance do sistema.

---

## Objetivo

Garantir que toda mutação de dados do usuário seja registrada de forma fire-and-forget e imutável em `audit_logs`, e que o usuário possa visualizar as últimas 100 operações em uma página de histórico de atividades com KPIs por domínio e tabela de eventos com timestamp relativo, badge de ação e detalhes filtrados.

## Requisitos Não-Funcionais

| ID     | Requisito            | Métrica de Aceite                                                                                                                   |
| ------ | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| RNF-01 | Fire-and-forget      | Falha em `AuditService.log` nunca retorna erro ao usuário nem interrompe a operação principal                                       |
| RNF-02 | Segurança            | Página exige autenticação; query filtra por `user_id` do JWT (S1)                                                                   |
| RNF-03 | Sem PII em `changes` | Campos `user_id`, senhas, tokens, `photo_url`, `photo_thumbnail_url` não são gravados nem exibidos                                  |
| RNF-04 | Imutabilidade        | Nenhuma tentativa de `UPDATE`/`DELETE` em `audit_logs` (via qualquer client, inclusive service role) tem efeito — bloqueado por RLS |

## Critérios de Aceite

- [ ] CA-01: Criar uma despesa via API → entrada `{ action: "Criação de Despesa", table_name: "expenses" }` aparece em `audit_logs` na página Histórico de Atividades
- [ ] CA-02: Falha simulada no insert de `audit_logs` (ex: timeout) → operação principal (criar despesa) retorna sucesso normalmente
- [ ] CA-03: Página `/atividades` sem sessão → redirect para `/login` (via `apps/web/middleware.ts`, ver changelog v1.2)
- [ ] CA-04: Página exibe KPI "Total" igual ao número de linhas na tabela de eventos
- [ ] CA-05: Coluna "Detalhes" não exibe campos `user_id`, `deleted_at`, `photo_url` ou `photo_thumbnail_url`
- [ ] CA-06: Entrada com `created_at` de 30 segundos atrás exibe "agora"
- [ ] CA-07: Entrada com `created_at` de 90 minutos atrás exibe "1h atrás"
- [ ] CA-08: `AuditService.log()` no backend sempre inclui `timestamp` no campo `changes`
- [ ] CA-09: Após `DELETE /users/me`, registros em `audit_logs` do usuário têm `user_id = NULL` (não são excluídos)
- [ ] CA-10: Tentativa de `UPDATE`/`DELETE` em uma linha de `audit_logs` (autenticado como o próprio dono da linha) não altera/remove o registro
- [ ] CA-11: Uma requisição autenticada que gera mutação tem `changes.requestId` preenchido em `audit_logs` igual ao `X-Request-Id` retornado na resposta

## Fora de Escopo

- Paginação do audit log (fixo em 100 entradas no MVP) — **revisitar antes da Fase 9** (usuários pagantes reais, LGPD Art. 18 — portabilidade de dados)
- Filtros por domínio, período ou tipo de ação na página Histórico de Atividades
- Exportação do audit log em CSV — mesmo gatilho de revisão da paginação acima
- Visualização do audit log por admin (SPEC-20260521-004 cobre `GET /admin/audit-logs`)
- Alertas em tempo real via websocket ou polling
- Registro de tentativas falhas/negadas (ex: tentativa de acessar recurso de outro usuário) — hoje cobertas apenas pela observabilidade técnica (`SPEC-20260716-002`, Sentry/Pino), não pelo audit trail de compliance; avaliar se vira requisito quando houver necessidade de auditoria de segurança formal
- **Audit log de operações em `analytics` e `dashboard`**: esses módulos não realizam mutação de dado financeiro ou pessoal sensível relevante a C2 — decisão mantida, sem revisão prevista

## Notas Técnicas

### Escritor único: `AuditService` (backend)

Toda escrita em `audit_logs` passa por `apps/api/src/shared/audit/audit.service.ts` (`AuditService.log()`), chamado de forma fire-and-forget (`void this.auditService.log(...)`) pelos services de domínio. Não existe (nem existiu) escrita direta a partir do frontend — o projeto não adotou Server Actions do Next.js para mutação (T3.9). Isso elimina o risco de formatos divergentes de `action`/`changes` entre duas implementações.

### Imutabilidade via RLS

`audit_logs` tem RLS habilitado desde `supabase/migrations/20260712172047_rls_policies.sql`, com quatro policies: `audit_logs_select_own` (SELECT filtrado por `auth.uid() = user_id`), `audit_logs_insert_own` (INSERT exige `user_id` do próprio usuário ou `NULL`), `audit_logs_no_update` e `audit_logs_no_delete` (ambas `USING (false)`, bloqueando qualquer alteração/remoção, inclusive por engano via service role em código de aplicação — a proteção é no banco, não apenas na camada de API). Isso satisfaz RF-04/RNF-04 e é uma boa prática central de audit trail (trilha à prova de adulteração) que a versão anterior desta spec não formalizava como requisito.

### `record_id`

`record_id` é `UUID NOT NULL` no banco e sempre recebe um ID real de recurso, gerado pelo próprio banco ou lido do registro existente — não há mais o risco de valores como `'new'` sendo passados (esse cenário só existia no fluxo de Server Actions que nunca foi implementado).

### Cobertura de ações

Cobertura hoje (via `grep` por chamadas a `AuditService.log()`): `auth` (REGISTER/LOGIN), `admin`, `users`, `vehicles`, `expenses`, `maintenances`, `fines`, `recurring-costs`, `odometer-cycles`. Não cobertos: `categories`, `vehicle-groups` (decisão original desta spec) e `preferences`, `analytics`, `dashboard`, `expense-templates` (módulos que não existiam quando esta spec foi escrita — decisão de manter fora de escopo registrada em 2026-07-18, ver seção "Fora de Escopo").
