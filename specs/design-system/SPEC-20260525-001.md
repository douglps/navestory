**Status:** approved
**Criada em:** 2026-05-25
**Autor:** Douglas Lopes (lps.doug@protonmail.com)
**Revisores:** Douglas Lopes, com agentes `Explore` (inventário de código real) e `design-system` (padrões de mercado 2026)

## 1. Contexto

**Correção (v0.2, 2026-07-19):** a versão 1.0 desta seção afirmava que `packages/ui` já possuía "componentes base bem estruturados (`Button`, `Input`, `StatsCard`, `Card`, `Table`)". Isso nunca foi verdade neste repositório — auditoria de código em 2026-07-19 confirma que `packages/ui/src/components/` contém apenas `masked-input.tsx`. Não existe `Button`/`Input`/`StatsCard`/`Card`/`Table` em `packages/ui` nem em `apps/web`. O texto original era resíduo de outro contexto/projeto, mesmo padrão de divergência já visto em `SPEC-20260602-001` (IMPACTO-032).

Consequência direta: como vários componentes desta spec presumem essa base (`KpiCard` "evolui o `StatsCard` existente", §5.1; `Alert`/`EmptyState` usam `Card` como container implícito), **`Button`, `Card` e `Table` entram no escopo de T8.1 como pré-requisito**, construídos antes ou junto dos 11 componentes originais — ver §4.2, §10 e §12.

Para suportar o roadmap do dashboard mobile-first de gestão de frota, este spec documenta os grupos de novos componentes com exemplos de código prontos para implementação.

Todos os componentes seguem o padrão estabelecido, **revisado em 2026-07-19 após estudo pré-implementação com os agentes `Explore` e `design-system`** (mesmo padrão de revisão já usado em T3.9/T5.1/T5.4/T7.1 — ver `matrices/impacto.md`, IMPACTO-038):

- **Tailwind CSS v3.4.17** — **correção v0.3:** a menção anterior a "variáveis OKLCH do `globals.css`" era incorreta, mesma categoria de erro do §1 original sobre `Button`/`Card`/`Table`; `globals.css` não define nenhum token hoje (ver §4.1). Tokens entram como pré-requisito 0 desta spec.
- **shadcn/ui v4** como referência visual, mas **primitivos headless 100% Radix** (`@radix-ui/react-*` + `cmdk`) — decisão v0.2: **`@base-ui/react` descartado**, para não fragmentar a árvore de dependências headless com uma 3ª API de composição convivendo com `@radix-ui/react-dialog`/`vaul` já em produção desde T5.4. Ver decisão registrada em IMPACTO-038.
- **CVA** (`class-variance-authority`) para variantes — dependência de estilo nova desta spec, ainda não instalada em nenhum `package.json` do monorepo
- **Ícones híbridos** (decisão v0.2, ver §4.3): `React.ReactNode` (emoji, mantendo o padrão de T5.4) para ícones decorativos; SVG inline fixo, embutido no próprio componente e sem dependência nova, para os 2 pontos onde o ícone é semântico (variante de `Alert`, indicador de estado de `Steps`). `lucide-react` **não** é instalado por esta spec.
- **Sem Storybook** (decisão v0.2, ver §11): documentação/isolamento via testes de interação (`vitest` + `@testing-library/react`, já instalados), não `.stories.tsx`. O script `storybook` órfão em `packages/ui/package.json` deve ser removido na implementação.
- **`jest-axe`/`@axe-core`** (novo em v0.3, ver §4.4) — critério de aceite de todos os componentes-base, dependência nova de teste
- **Mobile-first** — touch targets mínimos de 44px em mobile, compactados em `md:`

## 3. Histórias de Usuário e Critérios de Aceitação

**Persona P1 — Douglas, mantenedor solo do Nave**, consumindo os componentes ao construir/migrar telas.
**Persona P2 — Gestor de frota**, usuário final que vê o resultado visual/comportamental dos componentes.

### STORY-01 — Estados vazios consistentes
Como **P2**, quero ver uma orientação clara e uma ação sugerida quando uma listagem não tem dados, para saber o que fazer em seguida em vez de encarar uma tela em branco.

- Dado que a listagem de veículos/despesas/manutenções não tem nenhum registro, quando a página carrega, então um `EmptyState` exibe ícone, título, descrição e um botão de ação primária (ex: "Adicionar veículo").
- Dado que uma busca/filtro não retorna resultados, quando o usuário aplica o filtro, então um `EmptyState` `size="sm"` exibe "Nenhum resultado" com ação "Limpar filtros".

### STORY-02 — Feedback de erro/aviso confiável entre plataformas
Como **P2**, quero que alertas de erro/aviso sejam sempre legíveis e visualmente inequívocos, para não confundir uma mensagem de sucesso com uma de erro por causa de um ícone mal renderizado no meu celular.

- Dado que uma manutenção está vencida, quando a tela `Alert` correspondente é renderizada, então o ícone da variante `warning` é um SVG fixo do componente (não emoji), com `role="status"` e cor/forma idênticas em qualquer navegador/SO.
- Dado que um leitor de tela está ativo, quando o `Alert` é anunciado, então o texto lido inclui a variante ("Atenção", "Erro") de forma explícita, não dependente da interpretação do ícone.

### STORY-03 — Notificações unificadas
Como **P1**, quero um único mecanismo de toast reaproveitável, para não criar um 4º componente de notificação ad hoc toda vez que uma feature nova precisar avisar o usuário.

- Dado que uma ação de CRUD é concluída (ex: despesa salva), quando `pushToast({variant: "success", title: "..."})` é chamado, então um item aparece na fila de `toasts` do `ui-store` e desaparece sozinho após `duration` (padrão 4000ms).
- Dado que os 3 toasts existentes (`ContextStaleToast`, `ServiceWorkerUpdateToast`, `OfflineWriteBlockedToast`) são migrados para a fila genérica, quando qualquer um deles dispara, então o comportamento visual observado pelo usuário (posição, auto-dismiss ou persistência, botão de ação) permanece o mesmo de antes da migração — ver §7.2.

### STORY-04 — Métrica com tendência no dashboard
Como **P2**, quero ver rapidamente se um indicador de frota está piorando ou melhorando, para agir antes que o problema cresça.

- Dado que uma métrica tem histórico de 6+ pontos, quando o `KpiCard` renderiza, então uma sparkline SVG mostra a tendência e a seta (`↑`/`↓`) usa a cor correta considerando `reverseTrend` (ex: custo subindo = `danger`).
- Dado que os dados ainda estão carregando, quando `loading={true}`, então um skeleton com pulse substitui ícone/valor/sparkline sem quebrar o layout (`min-w-[150px] max-w-[220px]` preservado).

### STORY-05 — Busca de veículo em formulários
Como **P2** cadastrando uma despesa/manutenção, quero buscar o veículo por placa ou modelo digitando, para não precisar rolar uma lista longa em uma frota grande.

- Dado que a frota tem 20+ veículos, quando o usuário digita "ABC" no `Combobox`, então a lista filtra por placa/modelo em tempo real, sem chamada de rede adicional (filtro client-side sobre os veículos já carregados).
- Dado que nenhum veículo corresponde ao termo buscado, quando a lista filtra para zero itens, então `emptyMessage` ("Nenhum veículo encontrado") é exibido dentro do próprio popover.

### STORY-06 — Base visual reaproveitável
Como **P1**, quero `Button`/`Card`/`Table` prontos em `packages/ui` antes de construir os componentes de nível mais alto, para não duplicar CSS de botão/cartão/tabela pela 3ª vez no projeto (já duplicado em `FleetKpis.tsx` e `expenses/page.tsx` — ver IMPACTO-038).

- Dado que um componente novo (ex: `KpiCard`) precisa de um container com sombra/borda padrão, quando ele é implementado, então reutiliza `<Card>` de `packages/ui` em vez de declarar `className` de card inline.
- Dado que uma tela hoje usa `<table>` HTML puro com classes ad hoc, quando ela é migrada, então passa a usar `<Table>`/`<TableRow>`/`<TableCell>` de `packages/ui`, preservando o padrão "two-row table" já documentado em §9.1.

## 4. Fundamentos Adicionados em v0.2/v0.3

### 4.1 Tokens de Design (novo em v0.3 — pré-requisito 0, bloqueia §4.2)

**Achado crítico (v0.3, 2026-07-19):** a v0.2 desta spec ainda presumia, sem verificar, que `globals.css` já tinha "variáveis OKLCH" (herdado sem checagem do texto da v1.0 — mesma categoria de erro já corrigida em §1 para `Button`/`Card`/`Table`, só que desta vez não peguei na primeira revisão). Auditoria de código confirma: `apps/web/tailwind.config.ts` tem `theme.extend: {}` vazio, `apps/web/src/app/globals.css` tem só as 3 diretivas `@tailwind base/components/utilities` — nenhuma variável CSS, nenhum `:root {}`, Tailwind ainda em v3.4.17 (não v4). **Consequência prática:** classes já usadas em dezenas de arquivos de produção (`bg-muted`, `text-primary`, `border-l-primary`, `bg-muted-foreground/30` — vistas em `sidebar.tsx`, `analytics/page.tsx`, `atividades/page.tsx`, `expenses/page.tsx`, entre outros) **não têm definição em lugar nenhum e não geram CSS** — são classes mortas em produção hoje, silenciosamente sem efeito. Ver `matrices/impacto.md`, IMPACTO-038 (adendo v0.3).

**Escopo desta seção:** antes de construir `Button`/`Card`/`Table` (§4.2) ou qualquer componente de §5–§8, definir os tokens reais:

1. Auditar as telas existentes para levantar quais nomes semânticos (`primary`, `muted`, `success`, `danger`, `warning`, `info`) e quais valores de cor/espaçamento/raio já são referenciados (mesmo que hoje sem efeito), evitando redefinir do zero sem considerar a intenção original do código.
2. Formalizar os tokens em `packages/ui/src/tokens/` (TypeScript — `colors.ts`, `spacing.ts`, `radius.ts`), **não** em um pacote novo (`packages/design-tokens`) — decisão v0.3: o único consumidor real hoje é `apps/web`; um pacote separado adiciona `package.json`/build step próprios para uma reutilização multi-plataforma (mobile, PDF) que não está no roadmap do Nave. Promover a pacote próprio só se/quando um 2º consumidor real aparecer.
3. Aplicar os tokens em `tailwind.config.ts` (`theme.extend.colors`, `theme.extend.spacing`, etc.) **e** em `globals.css` (`@layer base { :root { --primary: ...; } }`) — o app continua em Tailwind v3, então a fonte de verdade é o `tailwind.config.ts` TypeScript (não o `@theme` CSS-first, exclusivo do v4); os tokens em `packages/ui/src/tokens/` alimentam esse config, não o contrário.
4. Nenhum componente de §4.2 em diante usa valor de cor/espaçamento solto (`className="text-[#f00]"` ou equivalente) — sempre via token.

### 4.2 Base — `Button`, `Card`, `Table`

> Depende dos tokens definidos em §4.1 — não construir com valores de cor/espaçamento soltos.

Pré-requisito descoberto durante o estudo pré-implementação (§1): nenhum dos três existe hoje. Escopo mínimo necessário para desbloquear os demais componentes desta spec — API completa (todas as variantes) fica para uma iteração futura se necessário; aqui só o suficiente para os componentes de §5–§8 não ficarem bloqueados.

```tsx
// Button — variantes cobrindo os usos já vistos no código real (primary, secondary, ghost, outline)
interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: "default" | "outline" | "ghost" | "destructive"
  size?: "sm" | "md" | "lg"
  loading?: boolean
}

// Card — container padrão, substitui o `className="rounded border p-3"` duplicado em
// FleetKpis.tsx e expenses/page.tsx (ver IMPACTO-038)
interface CardProps extends React.HTMLAttributes<HTMLDivElement> {
  padding?: "sm" | "md" | "lg"
}

// Table — primitivos de tabela para o padrão "two-row table" já em uso (§9.1)
// Table, TableHeader, TableBody, TableRow, TableCell — API espelhando <table> semântico,
// já com `align-top` e zebra striping (bg-muted/15) aplicados via CVA nas linhas ímpares
```

Ambos usam CVA para variantes (`class-variance-authority`, mesma decisão de §1).

### 4.3 Diretriz de Ícones (React.ReactNode vs SVG semântico)

Decisão v0.2 após pesquisa de acessibilidade (WCAG SC 1.1.1, técnica H86) e observação de padrões de mercado (produtos de IA conversacional líderes usam SVG monoline para ícone funcional, nunca emoji de SO — emoji renderiza de forma não determinística entre Windows/macOS/Android). Distinção: **ícone decorativo** (reforço visual, substituível sem perda de informação) vs **ícone semântico** (estado que precisa ser inequívoco entre plataformas).

| Componente | Prop de ícone | Tipo | Justificativa |
|---|---|---|---|
| `KpiCard` | `icon` | `React.ReactNode` | Decorativo — número e label já comunicam o KPI |
| `Tabs` (item) | `icon` | `React.ReactNode` | Decorativo — label textual já é a informação primária |
| `EmptyState` | `icon` | `React.ReactNode` | Decorativo — texto da mensagem carrega o significado |
| `Combobox` (item) | `icon` | `React.ReactNode` | Decorativo |
| `Combobox` (chevron de abrir/fechar) | — | SVG fixo do componente | Parte do affordance de interação, não do conteúdo do consumidor |
| `Breadcrumb` | — | Sem prop de ícone | Separador tipográfico simples (`/`); não entra no debate |
| **`Alert`** | `icon` (override opcional) | **SVG fixo embutido no componente** (4 variantes: erro/sucesso/aviso/info, ~1KB cada) | **Semântico crítico** — variante precisa ser confiável entre plataformas (ex: alerta de falha de veículo) |
| **`Steps`** (indicador de estado do círculo) | — | **SVG fixo embutido** (✓/✗ do mesmo set do `Alert`) | Semântico parcial — progresso do fluxo lido por leitor de tela |
| `Steps` (ícone decorativo do passo, se houver) | `icon` | `React.ReactNode` | Decorativo |

Nenhuma linha desta tabela instala `lucide-react`. Os 4 SVGs fixos do `Alert`/`Steps` são embutidos como componentes internos (`AlertIcon`, não exportado), com `aria-hidden="true"` — o significado semântico é carregado pelo texto da variante (`role="status"`/`title`), não pelo ícone isoladamente, seguindo H86.

A `Sparkline` (§5.1) ganha `role="img" aria-label="Tendência: {trend.value}% {trend.label}"` no `<svg>` — ajuste de a11y sem mudar a abordagem (SVG manual, sem lib).

### 4.4 Acessibilidade Automatizada (novo em v0.3)

**Decisão:** `jest-axe`/`@axe-core` entram no escopo de T8.1 como critério de aceite dos 14 componentes de `packages/ui` (não fica para a spec de QA/E2E, `SPEC-20260716-003`, ainda `draft`). Não há nenhuma cobertura de acessibilidade automatizada hoje no projeto (`TESTS_SPEC.md`/`RULES.md` não mencionam).

**Escopo:** cada `[nome].test.tsx` (§11) inclui, além dos testes de interação já previstos, uma verificação `expect(await axe(container)).toHaveNoViolations()` sobre o estado padrão do componente (e, quando aplicável, sobre o estado de erro/variante — ex: `Alert` em cada uma das 4 variantes). Resolve a11y estrutural uma vez nos primitivos (labels, contraste mínimo do token, `aria-*` obrigatórios de cada primitivo Radix) em vez de repetir a verificação por tela consumidora.

**Fora de escopo desta spec:** testes de navegação por teclado end-to-end e leitor de tela real — isso é coberto pela suíte E2E (`SPEC-20260716-003`) quando ela avançar, não pelos testes unitários de componente aqui.

## 5. Data Display

### 5.1 KpiCard — Vertical com Sparkline

**Propósito:** exibir uma métrica chave com tendência e mini gráfico histórico. Evolui o padrão de `KpiTile`/`KpiCards` já duplicado em `FleetKpis.tsx` e `expenses/page.tsx` (ver IMPACTO-038), consolidando em um único componente reutilizável de `packages/ui`.

**Visual:**
```
┌─────────────────────────────┐
│ Combustível          ⛽     │
│                             │
│  R$ 4.820                   │
│  ↑ +12% vs mês anterior     │
│                             │
│  ▁▂▃▄▅▆▇█  (sparkline)     │
└─────────────────────────────┘
```

**Interface TypeScript:**
```tsx
interface KpiCardProps {
  title: string
  value: string | number
  unit?: string                      // ex: "km", "L", "R$"
  icon?: React.ReactNode             // decorativo — ver §4.3
  trend?: {
    value: number                    // percentual (+/-)
    label?: string                   // ex: "vs mês anterior"
  }
  sparkline?: number[]               // array de valores históricos (6–12 pontos)
  variant?: "success" | "danger" | "warning" | "info" | "neutral"
  reverseTrend?: boolean             // ex: custo: up = bad
  loading?: boolean
  className?: string
}
```

**Exemplo de uso:**
```tsx
<KpiCard
  title="Combustível"
  value="R$ 4.820"
  icon="⛽"
  trend={{ value: 12, label: "vs mês anterior" }}
  sparkline={[2100, 2800, 3200, 3900, 4100, 4200, 4820]}
  reverseTrend  // custo crescente = danger
/>
```

**Decisões de design:**
- Sparkline renderiza via SVG inline (sem dependência externa para um gráfico simples), com `role="img" aria-label` (§4.3)
- Cor da sparkline herda o status calculado (`success` / `danger` / `warning`)
- `loading={true}` exibe skeleton com animação pulse nos 3 blocos (ícone, valor, sparkline)
- Largura: `min-w-[150px] max-w-[220px]` — grids de 2×2 no mobile funcionam com `grid-cols-2`
- Construído sobre `<Card>` de `packages/ui` (§4.2), não com `className` de card duplicado

**Implementação sugerida para Sparkline (SVG inline):**
```tsx
function Sparkline({ values, color, ariaLabel }: { values: number[]; color: string; ariaLabel: string }) {
  const max = Math.max(...values)
  const min = Math.min(...values)
  const range = max - min || 1
  const w = 80, h = 24, step = w / (values.length - 1)

  const points = values
    .map((v, i) => `${i * step},${h - ((v - min) / range) * h}`)
    .join(" ")

  return (
    <svg width={w} height={h} className="overflow-visible" role="img" aria-label={ariaLabel}>
      <polyline
        points={points}
        fill="none"
        stroke={`oklch(var(--${color}))`}
        strokeWidth="1.5"
        strokeLinecap="round"
        strokeLinejoin="round"
      />
    </svg>
  )
}
```

## 6. Navigation

### 6.1 Tabs

**Propósito:** navegação contextual entre views (ex: "Veículos / Despesas / Manutenções" no detalhe de um veículo). Consolida as duas implementações manuais já existentes — `expenses/page.tsx` (sem ARIA) e `VehicleSpotlight.tsx` (com `role="tablist"`/`role="tab"`/`aria-selected` já corretos) — adotando o padrão de acessibilidade do segundo (ver IMPACTO-038).

**Interface TypeScript:**
```tsx
interface TabsProps {
  items: {
    value: string
    label: string
    icon?: React.ReactNode          // decorativo — ver §4.3
    badge?: string | number         // ex: contagem de alertas
    disabled?: boolean
  }[]
  defaultValue?: string
  value?: string
  onValueChange?: (value: string) => void
  variant?: "default" | "pills" | "underline"
}
```

**Variante `underline` (padrão no dashboard):**
```
  Visão Geral   Despesas(3)   Manutenções
  ───────────   ────────────
  ^ativo        ^ativo
```

**Variante `pills`:**
```
 [Visão Geral] [Despesas 3] [Manutenções]
  ─────────────
  ^ativo (bg preenchido)
```

**Exemplo de uso:**
```tsx
<Tabs
  variant="underline"
  defaultValue="overview"
  items={[
    { value: "overview", label: "Visão Geral", icon: "📊" },
    { value: "expenses", label: "Despesas", badge: 3 },
    { value: "maintenance", label: "Manutenções", icon: "🔧" },
  ]}
/>
```

**Implementação:** `@radix-ui/react-tabs` como primitivo headless (não `@base-ui/react` — ver §1), preservando `role="tab"`/`aria-selected` já validado em `VehicleSpotlight.tsx`.

### 6.2 Breadcrumb

**Propósito:** rastreabilidade de navegação em telas aninhadas. Não existe implementação prévia no código (navegação hoje é só via sidebar) — componente 100% novo.

**Interface TypeScript:**
```tsx
interface BreadcrumbProps {
  items: {
    label: string
    href?: string                   // undefined = item atual (sem link)
    icon?: React.ReactNode          // opcional, decorativo — sem ícone é o padrão (§4.3)
  }[]
  maxItems?: number                 // colapsa itens do meio com "..." quando excede
}
```

**Visual:**
```
Frota  /  Veículos  /  ABC-1234  /  Despesas
```

**Comportamento mobile:** quando `maxItems` é excedido, colapsa itens intermediários:
```
Frota  /  ...  /  Despesas
```

**Exemplo de uso:**
```tsx
<Breadcrumb
  items={[
    { label: "Frota", href: "/fleet" },
    { label: "Veículos", href: "/fleet/vehicles" },
    { label: "ABC-1234", href: "/fleet/vehicles/abc-1234" },
    { label: "Despesas" },          // item atual, sem link
  ]}
  maxItems={3}
/>
```

### 6.3 Steps — Wizard Horizontal

**Propósito:** indicador de progresso em fluxos de múltiplas etapas (ex: cadastro de veículo, onboarding). Não existe implementação prévia — `/vehicles/new` é single-page hoje (ver IMPACTO-038); componente 100% novo.

**Layout selecionado:** horizontal com conectores.

**Visual:**
```
  ●──────────●──────────○──────────○
 Dados      Veículo   Revisão   Confirmar
  ✓          atual
```

**Interface TypeScript:**
```tsx
interface StepsProps {
  steps: {
    id: string
    label: string
    description?: string
    icon?: React.ReactNode          // decorativo — ver §4.3
  }[]
  currentStep: number               // índice 0-based
  completedSteps?: number[]         // índices concluídos
  onStepClick?: (index: number) => void  // permite navegar para passos concluídos
}
```

**Estados de cada passo:**
- `completed` — círculo preenchido com ✓ (SVG fixo do set semântico, §4.3), cor `success`
- `current` — círculo com borda `primary`, label em bold
- `upcoming` — círculo vazio, label em `muted`
- `error` — círculo com ✗ (SVG fixo do set semântico, §4.3), cor `danger`

**Exemplo de uso:**
```tsx
<Steps
  steps={[
    { id: "personal", label: "Dados", description: "Informações pessoais" },
    { id: "vehicle", label: "Veículo", description: "Dados do veículo" },
    { id: "review", label: "Revisão" },
    { id: "confirm", label: "Confirmar" },
  ]}
  currentStep={1}
  completedSteps={[0]}
  onStepClick={(i) => setStep(i)}
/>
```

### 8.2 Toast

**Propósito:** notificações temporárias e não-bloqueantes (confirmações de ação, erros de request).

**Decisão v0.2 (registrada em IMPACTO-038):** a versão 1.0 desta seção propunha `sonner` ou `@base-ui/react/toast`. Nenhuma das duas é adotada. Em vez disso, generaliza-se o padrão já em produção — 3 componentes dedicados (`ContextStaleToast`, `ServiceWorkerUpdateToast`, `OfflineWriteBlockedToast`), cada um com campo próprio no `ui-store` Zustand — em uma **fila única** dentro do mesmo `ui-store`, mantendo o ADR-008 (Zustand só para estado client puro) sem exceção e sem dependência nova.

**Posição:** canto inferior direito (desktop) / topo centralizado (mobile) — preservado da v1.0.

**Visual:**
```
              ┌──────────────────────────────┐
              │  ✓  Veículo salvo com sucesso │
              │                           ✕  │
              └──────────────────────────────┘
```

**Interface TypeScript (implementação sobre o `ui-store` existente, não uma lib nova):**
```tsx
interface ToastItem {
  id: string
  variant?: "default" | "success" | "error" | "warning" | "info"
  title: string
  description?: string
  duration?: number                 // ms, padrão 4000 (0 = persistente, ex: swUpdateAvailable)
  action?: {
    label: string
    onClick: () => void
  }
}

// Extensão do ui-store.ts existente:
interface UIState {
  // ...campos já existentes (isMobileNavOpen, contextStaleNotice, etc.)
  toasts: ToastItem[]
  pushToast: (toast: Omit<ToastItem, "id">) => void
  dismissToast: (id: string) => void
}

// Hook fino de conveniência em packages/ui ou apps/web/src/lib/hooks:
function useToast() {
  const pushToast = useUIStore((s) => s.pushToast)
  return { toast: pushToast }
}
```

**Exemplo de uso (interface pública idêntica à v1.0 — só a implementação interna muda):**
```tsx
const { toast } = useToast()

toast({
  variant: "success",
  title: "Despesa registrada",
  description: "R$ 180,00 adicionado em Combustível",
  action: { label: "Desfazer", onClick: handleUndo },
})
```

**Plano de migração dos 3 toasts existentes:** `ContextStaleToast` (auto-dismiss 5s, sem ação), `ServiceWorkerUpdateToast` (persistente, botão "Recarregar" → `duration: 0`), `OfflineWriteBlockedToast` (auto-dismiss 5s, cor âmbar) passam a chamar `pushToast()` internamente em vez de setar seus campos dedicados (`contextStaleNotice`, `swUpdateAvailable`, `offlineWriteBlockedNotice`), que são removidos do `ui-store` na mesma tarefa. Componente `<ToastViewport />` novo em `packages/ui` renderiza a fila. **Verificação obrigatória na implementação:** comportamento visual observado pelo usuário (posição, timing, texto, ação) deve permanecer idêntico ao pré-migração — são specs já `approved` (`SPEC-20260602-001`, `SPEC-20260712-001`) sendo tocadas indiretamente, não é uma mudança de comportamento aprovada por esta spec.

## 9. Padrões de Listagem

### 9.1 Layout de Tabela em 2 Linhas (Two-Row Table)

**Propósito:** todas as tabelas de listagem do sistema usam um layout compacto de 4 colunas com conteúdo empilhado verticalmente na célula central, em vez de linhas longas com muitas colunas.

**Estrutura padrão:**

| Coluna | Conteúdo |
|--------|----------|
| **Data/Vencimento** | Data principal + data secundária (vencimento, conclusão) |
| **Detalhes** | Linha 1: entidade principal (veículo, etc.) · Linha 2: badges + descrição + tags |
| **Valor/Custo** | Valor monetário alinhado à direita |
| **Ações** | Botões de edição/exclusão (80px) |

**Visual:**
```
┌──────────┬─────────────────────────────────────┬──────────┬─────┐
│ Data     │ Detalhes                            │    Valor │     │
├──────────┼─────────────────────────────────────┼──────────┼─────┤
│ 15/06/26 │ Hilux SR5 (ABC-1234)                │  R$ 350  │ ··· │
│          │ [Combustível] Posto Shell · via Man. │          │     │
├──────────┼─────────────────────────────────────┼──────────┼─────┤
│ 14/06/26 │ Gol G8 (DEF-5678)                   │  R$ 120  │ ··· │
│          │ [Manutenção] Troca de óleo           │          │     │
└──────────┴─────────────────────────────────────┴──────────┴─────┘
```

**Regras de implementação:**
- Todas as células usam `align-top` para alinhar à primeira linha visual
- Zebra striping: linhas ímpares (índice 1, 3, 5...) recebem `bg-muted/15`
- A célula "Detalhes" empilha conteúdo com `mt-1` entre as duas linhas visuais
- Badges, descrições e tags na segunda linha usam `flex items-center gap-2`
- Hover: `hover:bg-muted/50 transition-colors`

**Exemplo de código:**
```tsx

    <TableCell className="align-top">
      <div>{/* Linha 1: info principal */}</div>
      <div className="flex items-center gap-2 mt-1">
        {/* Linha 2: badges + descrição + tags */}
      </div>
    </TableCell>
    <TableCell className="text-right align-top">...</TableCell>
    <TableCell className="align-top">...</TableCell>
  </TableRow>
))}
```

**Páginas que usam este padrão:**

- `/fines`
- `/maintenance`
- `/recurring-costs`

## 10. Ordem de Implementação Sugerida

Revisada em v0.2 para distinguir **migração** (componente já tem versão inline em produção — risco de regressão em tela que já funciona) de **greenfield** (não existe em lugar nenhum — sem risco de regressão, mas sem atalho de "copiar o que já existe").

| Prioridade | Componente | Tipo | Motivo |
|---|---|---|---|
| 0 | Tokens (cores, espaçamento, raio) | Greenfield (bloqueante absoluto) | Nada em §4.2+ deve usar valor solto; corrige classes mortas hoje em produção — ver §4.1 |
| 1 | `Button`, `Card`, `Table` | Greenfield (bloqueante) | Pré-requisito de quase todos os demais — ver §4.2 |
| 2 | `EmptyState` | Migração (6 duplicatas) | Bloqueia qualidade de todas as listagens vazias |
| 3 | `Alert` | Migração (padrão ad hoc em ~30 arquivos) | Necessário para feedbacks de formulário e notificações inline |
| 4 | `KpiCard` (com sparkline) | Migração (2 duplicatas) | Dashboard principal |
| 5 | `Toast` | Migração (3 componentes ad hoc) | Maior risco de regressão desta lista — toca 2 specs `approved` indiretamente (ver §8.2) |
| 6 | `Combobox` | Greenfield (substitui `<select>` nativo) | Formulários de despesas/manutenção (seleção de veículo) |
| 7 | `Tabs` | Migração (2 implementações, uma já acessível) | Detalhe de veículo e navegação contextual |
| 8 | `Steps` | Greenfield | Onboarding e wizard de cadastro de veículo |
| 9 | `DateRangePicker` | Greenfield | Filtros de relatórios (fase posterior) |
| 10 | `FileUpload` | Greenfield, sem consumidor imediato | Upload de comprovantes (fase posterior) |
| 11 | `ChartWrapper` | Migração (lógica duplicada 2x) | Padronização dos charts existentes |
| 12 | `Breadcrumb` | Greenfield | Navegação hierárquica (pode ser adiado) |

Critério de aceite transversal (§4.4): todo item de prioridade 1–12 inclui verificação `jest-axe` no respectivo `[nome].test.tsx` antes de ser considerado concluído.
