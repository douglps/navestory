# SPEC-20260602-004: Categorias Personalizadas de Despesa

**Status:** Aprovado

**Autor:** douglps

## Contexto

O sistema oferece 9 categorias padrão de despesa (`fuel`, `maintenance`, `washing`, `toll`, `insurance`, `tax`, `parking`, `fine`, `other`). Usuários com necessidades específicas (ex.: "pedágio noturno", "aluguel de box", "uniforme de motorista") precisam criar categorias próprias.

Um mecanismo de categorias personalizadas foi implementado em duas camadas que não estão integradas entre si:

- **Legado (parcialmente ativo):** array de strings em `profiles.preferences.expense_categories`. O frontend (`ExpenseForm`) ainda lê desse campo; os labels exibidos são idênticos ao `value` bruto (sem rótulo formatado).
- **Nova tabela (backend implementado, frontend pendente):** tabela `user_categories` com RLS, constraints de DB e API REST completa em `GET /categories`, `POST /categories`, `DELETE /categories/:id`.

Esta spec formaliza o comportamento esperado do sistema completo e documenta o gap de integração atual.

---

## Objetivo

Permitir que o usuário crie e remova categorias nomeadas (com `value` slug + `label` legível), que apareçam mescladas às categorias padrão em todos os formulários de despesa, com limite de 20 por usuário.

---

## Requisitos Funcionais

| ID | Requisito | Prioridade |
|----|-----------|------------|
| RF-01 | `GET /categories` retorna `{ default: [...], custom: [...] }` — padrões fixos do sistema + personalizadas do usuário autenticado, ordenadas por `label` ascendente | Alta |
| RF-02 | `POST /categories` cria uma categoria com `value` (slug `^[a-z0-9_-]+$`, 1–50 chars) e `label` (1–100 chars) | Alta |
| RF-03 | `value` deve ser único por usuário — tentativa de criar com `value` duplicado retorna 409 | Alta |
| RF-04 | `value` não pode coincidir com o `value` de nenhuma categoria padrão — tentativa retorna 409 com mensagem específica | Alta |
| RF-05 | Limite de 20 categorias personalizadas por usuário — tentativa de criar a 21ª retorna 422 | Alta |
| RF-06 | `DELETE /categories/:id` remove a categoria se pertencer ao usuário; retorna 404 se não encontrada ou de outro usuário | Alta |
| RF-07 | `ExpenseForm` exibe categorias padrão + personalizadas mescladas sem duplicatas; categorias personalizadas exibem o `label` humano, não o `value` bruto | Alta |
| RF-08 | A mesclagem no `ExpenseForm` mantém as categorias padrão no topo da lista; personalizadas aparecem após | Média |

## Critérios de Aceite

- [ ] CA-01: `POST /categories` com `{ value: "fuel_premium", label: "Gasolina Aditivada" }` cria e retorna a categoria
- [ ] CA-02: `POST /categories` com `{ value: "fuel", label: "Qualquer" }` retorna 409 ("já é uma categoria padrão")
- [ ] CA-03: `POST /categories` com `{ value: "fuel_premium", label: "X" }` quando já existe retorna 409
- [ ] CA-04: `POST /categories` quando o usuário já tem 20 categorias personalizadas retorna 422
- [ ] CA-05: `POST /categories` com `{ value: "Fuel Premium", label: "X" }` retorna 400 (maiúsculas/espaços no slug)
- [ ] CA-06: `DELETE /categories/:id` para categoria de outro usuário retorna 404
- [ ] CA-07: `GET /categories` retorna campo `default` com exatamente 9 itens e `custom` com as categorias do usuário
- [ ] CA-08: `ExpenseForm` com `customCategories` preenchidas exibe o `label` da categoria personalizada no dropdown, não o `value` bruto
- [ ] CA-09: Excluir conta via `DELETE /users/me` — consulta `user_categories` para aquele `user_id` retorna zero registros

## Notas Técnicas

### Gap de integração: dois sistemas paralelos

O frontend em `/expenses/new` **ainda lê categorias de `profiles.preferences.expense_categories`** (array de `string[]`), não da nova API `GET /categories`. Isso significa:

1. Categorias criadas via `POST /categories` **não aparecem** no `ExpenseForm` até que o frontend seja migrado.
2. A prop `customCategories: string[]` do `ExpenseForm` recebe apenas os `value`s; o mapeamento `{ value: c, label: c }` faz com que o dropdown exiba o slug bruto (ex: `"fuel_premium"`) em vez do label legível (`"Gasolina Aditivada"`).

**Migração necessária** na página `/expenses/new`:
```ts
// Atual (legado):
const customCategories = profile?.preferences?.expense_categories ?? [];

// Correto (após migração):
const { data: categoriesData } = await api.get('/categories');
// customCategories = categoriesData.custom.map(c => ({ value: c.value, label: c.label }))
```

E a prop do `ExpenseForm` deve mudar de `customCategories: string[]` para `customCategories: { value: string; label: string }[]`.

### Constraint de unicidade no banco
`UNIQUE(user_id, value)` está no banco (migration `20260713210000_user_categories_unique_value.sql`, adicionada em T2.3 — a migration consolidada original não incluía essa constraint, gap encontrado durante a implementação). `CategoriesService.create` trata o erro Postgres `23505` explicitamente e relança como `ConflictException` (409).

### Hard-delete
Categorias personalizadas usam hard-delete (como grupos). Despesas que referenciam um `category` cujo valor pertencia a uma categoria personalizada excluída continuam existindo com o `value` bruto — sem cascade de categoria em despesas, pois `category` é um campo TEXT, não FK.
