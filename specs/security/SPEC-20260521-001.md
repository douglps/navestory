## Contexto

Análise arquitetural de 2026-05-21 identificou vulnerabilidades críticas no código existente que comprometem a integridade do audit log, expõem erros internos ao cliente e mantêm configuração de variável de ambiente incorreta no backend.

## Problemas

| # | Problema | Severidade | Arquivo |
|---|----------|-----------|---------|
| P1 | `NEXT_PUBLIC_SUPABASE_URL` usado no NestJS (prefixo de cliente Next.js em servidor) | Crítico | `apps/api/src/modules/auth/auth.module.ts` |
| P2 | `audit_logs` insert com campos incorretos (`event`/`metadata`) — schema exige `action`/`table_name`/`record_id`/`changes` — falha silenciosa | Crítico | `apps/api/src/modules/auth/auth.service.ts` |
| P3 | `http-exception.filter.ts` vazio — erros internos do Supabase/Postgres expostos ao cliente | Alto | `apps/api/src/common/filters/http-exception.filter.ts` |
| P4 | Rate limit de auth endpoints igual ao global (10 req/min) — insuficiente contra brute force | Importante | `apps/api/src/modules/auth/auth.controller.ts` |
| P5 | Rollback ausente nas 4 migrations existentes | Importante | `supabase/migrations/` |
| P6 | `SUPABASE_SERVICE_ROLE_KEY` não validado no Joi (usado em auth.module sem validação) | Médio | `apps/api/src/config/env.validation.ts` |
| P7 | `console.log` em main.ts (viola regra de sem logs em produção) | Baixo | `apps/api/src/main.ts` |

## Requisitos

### RF-SEC-001 — Corrigir variável de ambiente no auth module
- `NEXT_PUBLIC_SUPABASE_URL` → `SUPABASE_URL` em `auth.module.ts`
- SERVICE_ROLE_KEY continua justificado para operações server-side de auth + audit log (documentado)

### RF-SEC-002 — Corrigir insert em audit_logs
- Campos: `action` (string), `table_name` (string), `record_id` (UUID), `changes` (JSONB)
- Erros de logAudit devem ser capturados e logados sem propagar exceção (audit não pode derrubar fluxo)
- Valores para auth events: `action = 'REGISTER'|'LOGIN'`, `table_name = 'auth'`, `record_id = userId`

### RF-SEC-003 — Implementar HttpExceptionFilter global
- Capturar todas as exceções (HttpException + erros genéricos)
- Em produção: retornar mensagem genérica para erros 5xx
- Em desenvolvimento: incluir detalhes no response
- Nunca expor stack trace, query SQL, ou detalhes de schema ao cliente
- Logar detalhes internamente via NestJS Logger
- Registrar no `main.ts` via `app.useGlobalFilters()`

### RF-SEC-004 — Ajustar rate limit de auth endpoints
- `POST /auth/register`: 5 req por 15 minutos por IP
- `POST /auth/login`: 10 req por 15 minutos por IP
- Manter global de 100 req/60s para demais endpoints

### RF-SEC-005 — Criar rollback scripts para migrations
- Criar `supabase/migrations/rollback/` com 4 arquivos `_down.sql`
- Cada down script deve reverter exatamente o que o up script criou

### RF-SEC-006 — Validar SUPABASE_SERVICE_ROLE_KEY no Joi
- Adicionar validação obrigatória em `env.validation.ts`

### RF-SEC-007 — Substituir console.log em main.ts
- Usar `Logger` do NestJS

## Critérios de Aceite

- [ ] `SUPABASE_URL` (sem prefixo `NEXT_PUBLIC_`) em auth.module.ts
- [ ] audit_logs insertado com campos corretos (verificável via Supabase Studio)
- [ ] `logAudit` não propaga exceção — falha capturada e logada
- [ ] HttpExceptionFilter retorna `{ statusCode, message, timestamp }` para todos os erros
- [ ] Erros 5xx em produção retornam mensagem genérica (sem stack/SQL)
- [ ] Rate limit de login: 10/15min; register: 5/15min
- [ ] 4 arquivos `_down.sql` criados e revisados
- [ ] `SUPABASE_SERVICE_ROLE_KEY` validado pelo Joi na startup
- [ ] `console.log` substituído por `Logger.log`
