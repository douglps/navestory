# SPEC-20260602-002: Gestão de Veículos (CRUD)

**Status:** Aprovado
**Criada em:** 2026-06-02
**Atualizada em:** 2026-06-02
**Autor:** douglps
**Revisores:** —

---

## Contexto

Veículo é a entidade central do Nave SaaS — toda despesa e manutenção está vinculada a um veículo. O módulo já existe e está implementado na API e no frontend, mas nunca teve spec formal. Este documento retroativamente formaliza os requisitos e regras de negócio do domínio de veículos para que possam ser referenciados por outras specs, casos de teste e futuras features.

---

## Objetivo

Permitir que o usuário cadastre, visualize, edite e remova veículos da sua frota, com soft-delete em cascata que preserva o histórico de despesas e manutenções vinculadas.

## Critérios de Aceite

- [ ] CA-01: `POST /vehicles` com `plate="ABC-1234"` persiste `plate="ABC1234"` no banco
- [ ] CA-02: `POST /vehicles` com `plate="AB1234"` retorna 400 (placa inválida — menos de 7 caracteres úteis, não corresponde ao padrão BR nem Mercosul)
- [ ] CA-03: `POST /vehicles` com `plate="ABC1D23"` aceita (Mercosul válido)
- [ ] CA-04: `GET /vehicles` não retorna veículos com `deleted_at IS NOT NULL`
- [ ] CA-05: `DELETE /vehicles/:id` seta `deleted_at` no veículo, nas despesas vinculadas e nas manutenções vinculadas com o mesmo timestamp
- [ ] CA-06: `DELETE /vehicles/:id` para veículo de outro usuário retorna 404
- [ ] CA-07: `PATCH /vehicles/:id` com campos parciais atualiza apenas os campos enviados
- [ ] CA-08: `GET /vehicles/:id` para veículo inexistente ou de outro usuário retorna 404
- [ ] CA-09: Veículo sem `deleted_at` com `status="workshop"` aparece na listagem de veículos ativos
- [ ] CA-10: `POST /vehicles` sem `vehicle_type` retorna 400

## Notas Técnicas

### Campos obrigatórios vs. opcionais
O schema do banco (`001_initial_schema.sql`) define apenas `plate`, `make`, `model`, `year` como `NOT NULL`. O campo `vehicle_type` é obrigatório no schema Zod (`createVehicleInputSchema`) mas não tem constraint no banco — a validação ocorre na camada de API via `ZodValidationPipe`.

### Placa sem UNIQUE constraint no banco
Não há constraint `UNIQUE` na coluna `plate` da tabela `vehicles`. A validação de formato é feita no `LicensePlate` VO (API) e no `vehicleBaseSchema` Zod (validators). Placas duplicadas do mesmo usuário são tecnicamente possíveis no banco — adicionar `UNIQUE(user_id, plate)` é recomendado como melhoria futura (R-VEH-02 formaliza o comportamento esperado).

### Soft-delete atômico
O `SupabaseVehicleRepository.delete()` executa três `Promise.all()` em paralelo: vehicle, expenses, maintenances. Se qualquer um falhar, a exceção é relançada — mas como não há transação distribuída explícita, falha parcial é teoricamente possível se o segundo ou terceiro update falhar após o primeiro ter sucedido. Melhoria: envolver em uma função RPC Supabase transacional.

### Cascade de FK no banco
A FK `expenses.vehicle_id → vehicles.id ON DELETE CASCADE` e `maintenances.vehicle_id → vehicles.id ON DELETE CASCADE` afetam apenas hard-delete. O soft-delete é gerenciado inteiramente na camada de aplicação.
